# Feature specification: extraction and durable document status

## Goal and status

- **Release feature:** 2 — extraction and durable document status.
- **Status:** In progress; specification approved by the user on 2026-11-02. Partial implementation has focused test coverage; Feature 2 has not passed its end-to-end acceptance checks.
- **Goal:** A token holder can follow a text-based PDF or DOCX from upload to a durable extracted or safely failed state, including after a document-service restart.
- **Context:** [First-release scope](../FIRST_RELEASE_SCOPE.md), [release plan](../superpowers/plans/2026-11-01-first-release.md), and [Feature 1 specification](01-anonymous-private-upload.md).

## Scope

- **Included:** Safe scanning and extraction, persisted text and metadata, bounded asynchronous work and restart recovery, token-protected status, safe failures, a minimal typed frontend status client, configuration and meaningful tests.
- **Excluded:** OCR, report generation, analysis handoff, retry UI, report UI, retention cleanup and a complete public deployment. Feature 4 owns the analysis handoff; Features 6 and 7 own the complete browser experience and deployment. This feature does not merge or remove services or replace Kafka.
- **Dependencies:** Feature 1 upload/access controls, PostgreSQL and persistent original-file storage, Java 21, an OS-supported parser resource boundary and a private scanner daemon. Scanner signatures and runtime must be available for the internet-facing profile. The development profile must clearly identify any reduced protection and must not be presented as public-ready.

## Current behavior

This section describes the Feature 1 baseline before the Feature 2 changes. See **Verification and handoff** for the current implementation and its limits.

- The checked-out Feature 1 upload stores a generated access-token verifier and expiry, a `PENDING` database row and a local file; an after-commit callback submits extraction to an in-memory executor. The gateway forwards `/api/documents/**`; the document service validates `X-Document-Token` for status, text and deletion. Angular currently posts to localhost, keeps only the returned ID and has no status client or polling.
- `ExtractionOrchestrator` executes Tika in the application JVM, and saves `PROCESSING`, extracted text, counts, `EXTRACTED` or `FAILED` within one transaction. `PROCESSING` is therefore not independently committed during parsing. The queue is in memory and there is no restart recovery. No scanner, parser time or output limit, or parser isolation is configured. Empty extracted text is currently treated as success. Exceptions and filenames may be logged and raw exception messages may be persisted.
- The entity already has extracted text, page and character count columns; `GET /api/documents/{id}` omits text but returns the internal status and error message. A text endpoint exists. Tika is pinned to 2.9.2; its suitability and supported upgrade need verification before selection. Success can publish an optional Kafka event containing extracted text when explicitly enabled; no consumer exists. Kafka is disabled in the local profile and must not be replaced as part of this feature without separate approval.
- `compose.dev.yaml` supplies local PostgreSQL, document-service, gateway and persistent volumes. The 2026-11-01 architecture discovery documents predate Feature 1 and contain historical statements that no longer describe this checkout. Feature 1 reports local tests and a synthetic upload/restart check, but its integration tests mock extraction; they do not establish Feature 2's requirements.

## Proposed behavior and interfaces

The user approved this specification on 2026-11-02. Implementation and verification are in progress; unchecked criteria below are not claims about current behavior.

### Lifecycle and API

- Commit `PENDING` with the file before work is eligible. Commit a processing transition before scanning or parsing; commit the terminal result in a separate short transaction. An interrupted `PENDING` or in-progress document is discovered and retried after restart. Use the database as the durable work source, bound admission and concurrent work, and do not lose work on executor rejection. The initial design targets one document-service instance; startup may reclaim its interrupted jobs only after the previous instance and its parser processes have stopped. Use atomic claims and guarded terminal writes so deletion or stale work cannot recreate a document. Multi-instance deployment requires a separate, tested lease/fencing design and is outside this feature.
- Retain token authorization and `Cache-Control: no-store` on `GET /api/documents/{id}`. Public statuses are `PENDING`, `EXTRACTING`, `EXTRACTED`, and `FAILED`. Map the existing stored `PROCESSING` to `EXTRACTING`; `EXTRACTED` is an explicit interim extension to the release vocabulary because Feature 2 does not perform analysis and must not claim `COMPLETED`. The user approved this contract on 2026-11-02. Add `ANALYZING` and `COMPLETED` with the later analysis features. Preserve upload response compatibility and document the existing `PROCESSING` to `EXTRACTING` API change before implementation.
- On success, atomically persist nonblank extracted text, actual character count and page count if known. A DOCX page count or unavailable PDF count may be `null`; do not invent a page count. Status responses never include extracted text. The existing token-protected text endpoint may return it. No success event or handoff occurs on failure; this feature adds no new analysis handoff. Keep existing optional Kafka code unchanged unless separately authorized; the intended release configuration must not publish document text to Kafka.
- On failure, persist `FAILED` and a stable, bounded, non-sensitive `errorCode`, with a generic user-safe message if needed. Distinguish at least unsupported/encrypted or empty text, unsafe archive, malware detected, scanner unavailable/timeout, parser timeout/resource limit, malformed document and internal failure. Do not expose raw parser/scanner errors, paths, filenames, document content or stack traces in the API. Define exact codes and retry policy before implementation; automatic recovery from an interrupted job is distinct from retrying a terminal failure.
- Add a typed frontend status request carrying `X-Document-Token` in a header, with no token in URL or logs. Full polling UI, session storage and reporting remain Feature 6. A synthetic gateway upload and repeated status reads must exercise the actual backend flow for this feature.

### Safety and deployment options

- **Selected option A (approved by user, 2026-11-02):** A bounded child parser process with operating-system-enforced memory/CPU/process limits, a wall-clock deadline and a maximum output size, plus a private local scanner daemon with a bounded deadline. Scan the stored file before parsing; scanner detection, timeout and outage fail closed in the internet-facing profile. The child process must be terminated and reaped on timeout or cancellation. JVM heap limits alone are not a complete memory boundary.
- **Public host:** Linux with cgroup v2, selected by the user on 2026-11-02. Local macOS development can use Docker; the actual cgroup delegation, limits and child-process lifecycle still need implementation and verification.
- **Alternative B:** Independently managed, resource-limited parser and scanner containers, keeping them private and bounding requests and concurrency. This offers a container boundary but introduces more deployment units and operational complexity.
- Option A does not permit parsing untrusted files in the application process as a public-profile fallback. A clean scan is not a guarantee of safety. Select a currently maintained Tika version after checking compatibility and security advisories; avoid adding a new framework or service without approval. The specific scanner and host-level enforcement mechanism must be recorded and verified; if the boundary cannot be enforced, the public profile must fail closed rather than silently run without it.
- Implementation research: Apache identifies the [Tika 3.x maintenance line](https://tika.apache.org/download) as supported and lists [3.3.3 released 2026-10-13](https://tika.apache.org/) and [security advisories](https://tika.apache.org/security.html); compatibility and dependencies remain untested. The [ClamAV daemon protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html) supports framed streaming without giving the daemon a document path; the scanner choice and actual integration remain unverified.
- Proposed configurable starting limits, subject to host and fixture validation: 10 MiB upload (Feature 1 default), 50 admitted pending/in-progress jobs, two concurrent parsers, 30-second parse deadline, 10-second scan deadline, 1,000,000 extracted characters, 128 MiB total DOCX expansion and 1,000 archive entries. Set a 512 MiB per-parser OS memory ceiling and an explicit CPU/process ceiling on the supported deployment host. Enforce archive limits while processing, rather than trusting declared ZIP sizes. Admission returns `503` and `Retry-After` before accepting work when capacity is full; enforce the cap atomically. Ensure type detection and scanning themselves are bounded, and do not allow untrusted archive contents to escape the isolation boundary.

## Security and privacy

Possession of a document ID or a forged user header never authorizes access. Tokens remain header-only, hashed at rest, and absent from logs. Originals and text stay on private persistent storage/database; no real legal documents or secrets belong in fixtures, logs, events or the repository. Scanner and parser interfaces are private. Sanitized operational logs may contain document IDs and safe error codes but not extracted text, raw parser output, file paths or sensitive filenames. The development profile is not suitable for public uploads until the full release protections are implemented and verified.

## Acceptance criteria

- [ ] A synthetic text PDF and DOCX uploaded through the gateway reach `EXTRACTED`; persisted nonblank text and character counts are correct, and page count is accurate when known.
- [ ] Token-protected polling shows committed pending/processing and terminal states; missing, incorrect or expired tokens and forged identity headers do not grant access. Status does not expose extracted text or sensitive error details.
- [ ] An empty or scanned-only PDF, encrypted PDF, malformed DOCX and excessive archive expansion reach a durable, distinguishable safe failure; no success handoff occurs.
- [ ] Scanner detection, timeout and outage fail closed before parsing in the internet-facing profile. Parser timeout, output and resource limits terminate work safely and leave an observable failure.
- [ ] Restart with queued or in-progress work recovers without silently losing it or running simultaneous claims; terminal results survive restart. Deletion during work cannot resurrect a record.
- [ ] Queue and concurrency bounds are exercised, including rejection and recovery; all input handling remains bounded. No tokens, document content, raw errors or sensitive file details appear in logs or events.
- [ ] The chosen isolation and scanner boundary is configured and tested as approved; public deployment is not claimed from local-only tests.
